# Controlled Activity / Operational Chat Implementation

Status: implemented baseline as of 2026-06-13.

## Objective

Add operational communication to Consflow without introducing a global social chat product. Messages stay tied to project work, domain records, decisions, blockers, evidence, reminders, and audit history.

## Implemented Scope

### Batch 1: Composer And Typed Activity API

- Extended activity requests with typed payloads, visibility, metadata, and validation.
- Preserved backend-generated `system_event` behavior.
- Added work-item activity composer and typed activity timeline labels.

### Batch 2: Project Threads And Domain Record Context

- Added project-level activity endpoints and list queries.
- Added scoped target support for project, work item, BOQ item, procurement request, stock movement, acceptance, rework, handover, payable, receivable, and payment records.
- Surfaced project activity in Project Operations without making it a global room.

### Batch 3: Mentions, Assignments, And Unread State

- Added user and role mentions.
- Added unread/read state per activity and user.
- Added `/my-work` communication attention queues for mentions, questions, blockers, reminders, and unread items.
- Limited role mentions to matching active project members.

### Batch 4: Attachments And Evidence Integration

- Added activity attachment references for evidence and documents.
- Connected file-note UI to existing evidence/document metadata.
- Kept binary upload/storage out of scope.
- Preserved client/internal visibility checks for attached records.

### Batch 5: Realtime Delivery

- Added SSE stream infrastructure in the Go/Fiber backend.
- Added project activity and `/my-work` attention streams.
- Used authenticated `fetch` streaming on the frontend so Bearer tokens stay in headers.
- Kept REST list endpoints as source of truth after reconnects and stream invalidations.

### Batch 6: QA And Handoff

- Updated active state documentation to mark the chat baseline complete.
- Captured validation status and future follow-up slices.

## Important Decisions

- Operational chat is activity-first, not room-first.
- `system_event` records are generated by backend workflow transitions, not user-created through the composer.
- Client-visible communication requires explicit visibility; internal cost, supplier, staff, and audit context stays hidden unless deliberately shared.
- Attachment support stores structured references to existing evidence/document records; it does not add binary storage.
- Realtime uses SSE instead of native `EventSource` because the frontend needs Bearer auth headers.
- The SSE hub is in-process. Multi-backend production deployment will need shared fanout, likely Redis pub/sub.

## Known Risks And Follow-Ups

- SSE baseline works for a single backend process, but multi-instance deployments need shared pub/sub fanout.
- Manual browser QA is still needed before calling realtime production-ready.
- Binary document upload/storage remains out of scope.
- Additional tests can harden client-visible attachment behavior and role-mention edge cases.
- Future domain-specific composers should stay scoped and typed rather than adding generic chat surfaces.
