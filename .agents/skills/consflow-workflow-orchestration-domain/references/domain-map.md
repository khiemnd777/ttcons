## Invariants

- Published pipeline template revisions are structurally immutable; structural edits require a new draft revision in the same `template_family_id` lineage. Node, Step and Connector inspectors remain available for read-only inspection; Connector Inspector must hide Save and disable stored label, condition/config and priority fields. Presentation-only layout remains mutable for actors with `pipeline.edit`: node coordinates and stored connector port sides may change atomically, but connector endpoint node IDs, ordering, conditions, steps/forms, definition semantics and runtime copies may not. The layout route derives endpoint node IDs from the stored edge and writes an audit event.
- Publish records `definition_hash`, `published_at`, and `published_by` together with its audit event in one fail-closed transaction; project runtime starts only from an exact published revision.
- `pipeline_runs.engine_version` and `pipeline_runs.template_definition_hash` snapshot the selected execution contract and are not refreshed from later revisions.
- Engine v2 run steps snapshot `form_required` and exact `form_version_id`; a submitted different form or synthetic legacy checklist cannot satisfy the gate.
- Runtime steps are deterministically ordered by `order_index,id`; do not reference a non-existent `pipeline_run_steps.created_at` column in run detail or completion-gate queries.
- UAT for official template automation must invoke stable engine-v2 `domain_action_key` actions through the hard-automation gate; display-name automation is legacy engine-v1 compatibility only.
- Engine v2 work items can mutate only inside the run's current node. Advancing a node requires all run steps/work items, exact forms, node approval, and mandatory automation events to be ready.
- Official template revision 2 is a new immutable lineage revision that inserts `Kế hoạch thi công` before `Thi công`; existing runs retain revision 1 snapshots. `NodeCompletionIssues` adds `CONSTRUCTION_HANDOFF_REQUIRED` only to `construction_planning` nodes until an activated handoff exists. Generated target-node work items remain pending until normal node advance makes them ready, so handoff does not bypass engine-v2 current-node execution rules. Handoff idempotency is scoped to the submitted source-form revision; a later form revision atomically cancels/replaces only still-pending generated rows and is rejected after execution, evidence or remediation has begun.
- Branch transitions compute every descendant reachable from unselected direct targets, subtract every node reachable from the selected target, then mark only the remaining pending branch-exclusive nodes `skipped`. Their pending steps and work items plus draft form instances become skipped/cancelled; convergence/shared descendants remain executable, and skipped nodes stay excluded from progress.
- Project Operations preserves those cancelled branch work items as read-only history and labels them as skipped; action queues and `CanActOnWorkItem` continue to exclude them. Runtime timeline completion treats `submitted` and `completed` steps as satisfied, while skipped/cancelled steps are counted separately and never inflate progress.
- The project Tổng quan presentation reuses runtime work-item priority and timeline data: next action order stays blocker -> waiting approval/review -> other open work, current-stage progress remains source-backed, and navigation labels may be Vietnamese without changing runtime status keys or gates.
- The project `Kế hoạch` route is a navigation-only action queue over the complete ordered pipeline-run step/work-item set. Runtime work-item status—not workflow-form draft state—controls actionable/waiting/future/completed grouping; form requirement/status and evidence remain supporting metadata. Its next-work priority is blocker -> waiting approval/review -> other open work, and it never performs step completion, approval, blocker resolution or node transition outside permission-gated detail/`Quy trình` surfaces.
- The project Workflow tab and `/projects/:id/pipeline` reuse one execution workspace that leads with current node, executable progress and one next-work CTA ordered blocker -> waiting approval/review -> other open work. Active nodes default to `Cần xử lý`; skipped/cancelled nodes default to `Đã bỏ qua` so read-only branch history remains immediately visible. Run-node request-approval, advance and block remain secondary controls and never bypass backend gates; recreate and block require explicit confirmation/input dialogs.
- The project Work tab is an operational queue over the complete scoped Project Operations `work_items` list: actionable work is the default, waiting approval/review and blocked work remain explicit attention queues, future `pending` work stays distinct, and completed/cancelled records remain available as history. List rows expose only navigation; transitions, forms, evidence and approvals remain inside permission-gated work-item detail.
- Engine v2 steps snapshot `surface_kind` and `domain_action_key`; work-item UI must route by this contract before any legacy text heuristic.
- Official contract steps 24 and 29-31/33 use `surface_kind='contract'`; step 32 remains the approval surface. Pending runtime steps receive the new surface/permission snapshot, while completed historical steps are not rewritten.
- Official quality steps 36-37 use `surface_kind='quality'` with `quality.create` and `quality.recurring_manage`; only pending runtime steps receive the new surface/permission snapshot.
- Official finance-management steps 42-45 and 48-52 use `project_finance.*` permissions and user-facing wording for internal cash-request handoff, material-cost capture and management closure. V83 updates future reusable template definitions only; it does not rewrite active/historical `pipeline_run_steps`, work items, answers, approvals, audit records or PDF artifacts. The finance primary surface routes future work to Tài chính công trình while any configured form/PDF remains supporting evidence.
- Submitting `builtin_construction_daily_report` invokes an idempotent operations-ledger bridge in the same transaction before workflow completion payload is persisted.
- The operations timeline consumes that bridge's structured daily-report answers without changing workflow completion semantics. Direct manual reports use their own typed create/update and report-evidence-upload contract, but still do not create work items, workflow form instances, approvals or completion events; new files remain normal work-item evidence. Any report with `workflow_form_instance_id` is read-only in Operations and rejects direct update/upload, preserving the source form as authoritative. Legacy summary rows remain readable. Outgoing work-item acceptance and the project acceptance workspace share `AcceptanceEditor.tsx`, while form/signature/PDF gates and work-item action permissions remain authoritative.
- Engine v2 hard `domain_action_key` automation runs before work-item completion. Blocked/failed outcomes are recorded idempotently and leave the work item incomplete; display-name dispatch remains legacy-only.
- Engine v2 node approvals snapshot structured `approval_policy_json` into the run and request. Supported modes are `any`, `all`, `quorum`, and `ordered`; stage, actor role, requester separation, comments, actions, and audit remain traceable. Pending-list responses add requester identity, actor/current-stage `capabilities`, `available_actions`, `decision_context` and target labels after project-scope filtering. Dashboard presents its scoped management queue with the requester and current required roles, including truthful fallbacks for incomplete legacy/test metadata; it shows actions only from server capability/action fields and marks non-decidable rows read-only. Project Workflow and the separate My Work node-approval lane reuse the same contract; node requests are never synthetic work items.
- Workflow-form template create/update/archive, node approval request and node block/complete transitions persist their audit event in the same transaction; an audit serialization/insert failure rolls back the state transition.
- Publish validation covers graph reachability/root/sink/cycle, required published form versions, answer-condition configuration, permission-key existence, and rejects any external-only role label in node responsibility, step responsibility or approval policy.
- Template layout/report presentation edits do not mutate existing run copies. Node coordinates, `condition_config.diagram` and template `report_config_json` are excluded from new definition hashes while all business condition keys remain hashed; cloning preserves the report configuration.
- Pipeline node `type` remains a technical template/runtime key. Pipeline Builder node cards and Node Inspector options share the frontend `nodeTypeValues`/`enumLabel` presentation contract: known official types render Vietnamese labels, while an unknown future key remains visibly readable through the raw fallback rather than being discarded.
- The global Progress Board is presentation only. It derives a normalized stage from each project's snapshotted current run/current node without editing templates, runtime copies, work items, approvals or branch history. `survey`, `design`, commercial node types, `construction_planning`, `construction`, acceptance/rework types, and handover/financial closure are grouped for scanning; completed runs override node grouping, no-run projects stay not-started, and unknown/custom node types remain in an explicit fallback column. Realtime events invalidate the snapshot but never carry transition commands or bypass runtime gates.
- Pipeline-template PDF export requires `pipeline.view` and reads the exact selected draft/published revision. It emits an on-demand A4 landscape Unicode definition snapshot whose header explicitly says `Revision định nghĩa` and `Trạng thái định nghĩa`. Page 1 topology derives from edge source/target independent of canvas positions; connector labels stay attached to their route. Section 3 labels checklist/document/photo as definition-level mandatory gates and states that the single Thi công step repeats by item/day. Optional report-only node references appear in appendix A; runtime/UAT state is never included. Export never changes template/runtime state, persists an artifact or writes audit.
- Cosmetic official-step text corrections require an additive migration and matching seed correction across template, runtime, work-item and form-instance display snapshots; they do not change statuses, answers, approvals, audit records or PDF artifacts.
- V68 keeps official revision-2 titles action-first and moves responsibility labels into template `required_role_ids`. It adds `Thiết kế`, `Sale`, `Pháp lý`, maps the reviewed technical-team responsibility to existing `Đội thi công`, updates existing display snapshots, and preserves runtime role/assignment snapshots so active and historical authorization does not change unexpectedly.
- V69 uses `đầu vào` as the collective workflow term for tổ đội, thầu phụ and material suppliers in aggregate step/form/node/edge labels. Entity-specific wording remains mandatory where negotiation, acceptance, payable settlement or supplier invoices identify a concrete party/material. Existing revision-2 updates are display-only: roles, assignments, statuses, answers, approvals, audit records, PDFs and published form schemas remain unchanged.
- Published workflow form versions are immutable runtime references.
- Workflow PDF export rows remain immutable audit evidence. V93 records deletion lifecycle separately: the actor needs the same active-work-item permissions as PDF generation, any `acceptance_records.pdf_export_id` reference blocks deletion, provider `Delete` removes Local/S3 bytes, a failed storage operation remains visible and retryable, and successful deletion atomically records tombstone, workflow event, work-item activity and audit before the artifact disappears from active lists.
- Workflow-form PDF bytes are rendered in memory as branded A4 portrait UTF-8 documents using embedded Noto Sans. User-facing values come from the published field definition: option labels replace raw enum keys, booleans/dates/currencies are localized, structured lists use labeled tables, vector signature strokes remain attached to signer/purpose/time/hash context, and V94 places checksum-verified company-seal images in fixed confirmation cards. V95 adds a mutable per-instance/per-purpose composition preference without mutating immutable signature/seal evidence: controls exist only when both kinds share a purpose, at least one kind must remain, no row defaults to both, and a purpose with one kind always includes that kind. The selected form is filtered before payload hashing, seal-byte loading and rendering; every immutable export/event/audit snapshot stores exact selected IDs/counts. `Tạo PDF` remains direct and creates no extra selection dialog. Project/node/step, export actor and export time are presentation metadata only; `payload_hash` covers the rendered immutable form snapshot and selected confirmations.
- Workflow-form instance `submitted` remains the persisted API/runtime status, but its work-item UI wording is `Chốt hồ sơ` / `Đã chốt`: submission locks the revision, records actor/time/events/activity/audit and satisfies configured form/checklist gates; by itself it has no recipient and creates no approval request. Contextual presentation must not change the shared `submitted` wording used by BOQ, accounting, acceptance or other real send/review flows.
- The `/workflow-forms` authoring UI must keep published versions read-only and make draft state explicit. Template/version switching or page unload warns when local draft fields differ from the loaded snapshot; publish and archive actions require deliberate confirmation. UI field/step/instance metrics must remain source-backed by the existing managed-template contract and must not imply a detailed usage list that the API does not provide.
- `required_role_ids` remains an array everywhere.
- V89 does not rewrite published template, pipeline-run or work-item role snapshots. Historical `Chủ đầu tư` labels remain readable and mixed internal roles continue acting under normal gates; new draft publication cannot require an external-only App actor.
- Work item completion respects required forms, evidence, signatures, approvals, and blockers. `workItemCompletionRequirements` is the canonical backend contract for both completion validation and work-item-detail presentation; an exact submitted engine-v2 workflow form satisfies its configured checklist gate, so clients must not independently infer checklist readiness from aggregate evidence.
- `/my-work` is the single adaptive actor-scoped role workbench and authenticated landing page, not a second workflow engine. It defaults to `all + need_action`, exposes `in_progress` and read-only `upcoming`, and carries complete project/node/step context plus server `readiness`. Non-terminal future work stays read-only under backend gates. Its `Chờ tôi duyệt` summary adds actor-decidable node approval records in a distinct lane while ordinary work-item paging remains unchanged; requester separation, current stage/roles and project scope come from `/approvals/pending?decidable_only=true`. Capability hints never replace mutation-time authorization, form, evidence, signature, approval or blocker enforcement.
- Project evidence listing is read/review presentation only: server-filtered history may include rejected evidence but excludes cancelled-work-item evidence; `can_review` mirrors the existing decision gate and never replaces backend enforcement or satisfies completion/form/approval gates.
- Project activity resolution is separate from work-item transitions: question/blocker/reminder metadata may be closed only by an authorized actor, and each resolution appends a system activity plus audit without bypassing work-item blocker or completion gates.
- Project activity replies and reactions are communication-only: replies inherit the parent context/visibility and reactions are active-state acknowledgements; neither can satisfy work-item evidence, form, approval, blocker, completion or runtime-node gates.
- Project activity comment edits and withdrawals are communication-only and author-scoped within 15 minutes. They append revisions/audit and never satisfy, reopen or bypass work-item evidence, form, approval, blocker, completion or runtime-node gates; typed operational activity is not mutable through these endpoints.
- Signatures and PDFs preserve revision, actor, hash, checksum, opaque storage provider/key and protected file access. V70 permits `s3` metadata but keeps artifact history immutable: the only accepted update is a same-key, provider-only `local -> s3` relocation; every other update and every delete still fail. V71 adds `NOT VALID` future-write checks requiring internal visual/PDF keys to be non-null, nonblank and canonical while preserving legacy invalid rows for operator inventory; it does not redefine the V70 triggers. Their generated objects use the shared storage registry; detail is loaded inside the mutation transaction before commit. A typed pre-commit failure deletes the new object, but an outcome-unknown commit error preserves it to avoid deleting a committed reference. Files are opened only after work-item view authorization before streaming.
- V94 adds reusable company seals without redefining a human signature. `seal_assets` stores admin-managed protected PNG-normalized resources; uploads decode only PNG/JPG/WebP, cap input and normalized output at 10 MB, reject SVG and oversized dimensions, and join the Local/S3 migration inventory. `workflow_form_seal_applications` is append-only audit evidence with actor/roles/time/purpose/revision/payload hash and an immutable asset reference. New applications require `seal.use`, a submitted form, active/current actor-actionable work item and its configured permission. Archiving an asset only removes it from new selection; historical visuals and generated PDFs remain readable. Seal applications never populate `workflow_form_signatures`, never satisfy acceptance/approval signature gates and never replace the contract current-version `approved_by` App signature.
- Workflow PDF generation remains in memory and writes only through the active shared storage provider. Default development storage requires the explicit repo-host `STORAGE_PATH`; S3 runtime neither registers nor writes a local adapter and never stages through the container filesystem. Existing `local` PDF/signature/evidence/invoice metadata and source objects remain intact until the explicit verified local-to-S3 migration updates provider metadata; there is no automatic deletion or dual-read fallback in normal S3 runtime.

## Cross-Domain Checks

- Pair with the source business domain when workflow forms create or summarize planning, construction, commercial, material, acceptance, or finance records.
- Check template authoring, runtime copies, work-item gates, activity, and frontend status labels together when changing workflow transitions.
- Do not let convenience UI bypass approval, required-form, evidence, signature, PDF, material, receivable, or blocker gates.

## Official Client Workflow Rev5

- V92 publishes immutable engine-4 template `40000000-0000-0000-0000-000000000024` from Rev4. It retains 15 unique node codes, 51 unique step codes and the accepted Rev4 business definition; existing runs and Rev3/Rev4 templates remain untouched.
- `project_intake.confirm` requires published form `client_project_intake_routing`. Field `entry_route` selects `survey_required|client_boq`; `client_boq_evidence` is visible and required only through generic `visibility_condition_json`/`validation_json.required_when` rules.
- Workflow-form instance detail decodes `workflow_form_answers.value_json` through its column-specific JSON decoder, preserving native string, number, boolean, null, object and array values without broadening the generic repository normalizer. Submitted/read-only route fields therefore continue satisfying visibility rules after reload.
