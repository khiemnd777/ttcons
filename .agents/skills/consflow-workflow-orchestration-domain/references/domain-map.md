# Workflow Orchestration Domain Map

## Canonical User-Facing Workflow Terminology

- The approved canonical Vietnamese vocabulary is `Giai đoạn` for Node, `Gói công việc` for Step and `Đầu việc` for Work Item. The official final workflow stage wording is `Bàn giao công trình và hồ sơ kế toán`; see `docs/workflow-terminology-agreement.md`.
- These names control agent communication and proposed user-facing labels only. Runtime and definition contracts continue to use stable technical keys such as `pipeline_template_nodes`, `pipeline_template_steps`, `pipeline_run_nodes`, `pipeline_run_steps`, `work_items`, `run_node_id`, `run_step_id`, `handover_finance`, `financial_closure`, permissions, business codes and event types.
- Applied migrations and historical template/run/work-item/form/audit/PDF snapshots are immutable. If the official current definition needs the renamed final stage, create an additive migration that publishes a new immutable revision and keep existing runs pinned; do not rewrite Rev8/Rev9 history.
- The final-stage rename does not by itself rename the standalone project-finance workspace. First searches for rollout: `NodeInspectorPanel|NodeLibraryPanel|NodeCard|ProjectStartupWizard|ProjectWorkspaceLayout|WorkItemPrimarySurface|pipelinePDFStepSemanticsNote|Khóa tài chính công trình|Tài chính công trình`.

## Required Procurement Automation Recovery

- Runtime Work Item completion still invokes `RunRequiredWorkflowAutomationForWorkItem` before any terminal state write. For `procurement.require_approved`, official engine-2 legacy runtime steps now receive the same read-only `business_source` recovery contract needed to explain that hard gate; this does not rebind, republish or mutate their template/run snapshots.
- A blocked outcome identifies the exact purchase source, while Work Item UI prefers current source inspection over stale event history, refreshes after a rejected Complete, displays `details.reason` and opens the canonical source dialog instead of the Complete action panel. Source approval is a separate commercial transition and never marks the Work Item/Run Step complete or advances the Node.
- First searches: `RunRequiredWorkflowAutomationForWorkItem|WorkflowBusinessSourceForWorkItem|automateClientInputProcurementGate|requiredAutomationPresentation|businessSourceNavigationPath`. Tests cover legacy runtime exposure, exact target/error details, all-blockers-resolved success and frontend navigation. No migration, approval policy, role, evidence/form gate or activity history rule changed.

## Invariants

- Pipeline's viewed stage is presentation state in `/projects/:id/pipeline?stage=<run_node_id>`, independent from the current execution node and work filters. `projectPipelinePath` and `projectPipelineReturnTo` in `workItemNavigation.ts` preserve the known work stage across Preparation, domain task context and Pipeline work returns. `PlanningPage` derives selection from the current URL so reload/history are consistent; unknown stage IDs fall back within the loaded timeline. Same-project return normalization preserves unrelated query/hash and never rewrites a different destination. Stage navigation does not advance runtime, mutate node/work-item status, authorize actions or change the execution summary's source.

- Project data-package references are immutable identifiers, not workflow mutations: `pipeline_ref` binds template UUID, revision and definition hash; Form/Field references bind published active form version UUIDs. XLSX and nested JSON v1 share one canonical request. Project import must fail closed when no ready published Pipeline or no valid published Form/Fields exist, and execute rechecks the selected Pipeline under lock before creating the project master. Import never starts a run, copies runtime nodes/steps, creates work items/form instances/answers or advances any workflow. Export may expose selected/runtime refs plus mismatch/missing state in XLSX or JSON for historical diagnosis without rebinding either side.
- Manual project startup orders master data, membership and runtime readiness explicitly. The shared wizard must persist the project before atomically adding members, and must not create a Pipeline Run or Work Item during either step. Startup readiness may expose additive whole-template operational-role coverage for presentation, derived from the selected immutable template revision and active project members; this projection neither mutates that revision/runtime nor adds a blocker for later-stage roles. Only the final existing `/projects/:id/start-pipeline` transition may materialize runtime nodes/steps and first Work Items after backend PM/template/first-step coverage succeeds; batch project import remains outside this wizard.
- Workflow Definition data packages provide definition portability, never runtime restore. The 12-sheet XLSX and nested `consflow.workflow-definition-package` JSON v1 replace package-internal UUID relationships with portable keys, stable role names and permission keys and feed the same validator/import transaction. JSON rejects duplicate, dangerous and unknown schema keys. Preview must block unresolved Form/Field/role/permission references, external-only roles, invalid graph/edge/surface semantics and target draft conflicts. Execute revalidates format/version/HMAC/reference fingerprint and creates only new draft Form versions and Pipeline revisions in one transaction, Forms before Pipelines; it never overwrites, publishes, starts a run, creates work items/Form instances, or rewrites historical definitions/runtime. Pipeline export with dependencies includes the exact referenced draft or published Form/Fields. Project readiness remains published-only, so imported drafts do not unblock project import until separately reviewed and published.

- Published pipeline template revisions are structurally immutable; structural edits require a new draft revision in the same `template_family_id` lineage. Node, Step and Connector inspectors remain available for read-only inspection; Connector Inspector must hide Save and disable stored label, condition/config and priority fields. Presentation-only layout remains mutable for actors with `pipeline.edit`: node coordinates and stored connector port sides may change atomically, but connector endpoint node IDs, ordering, conditions, steps/forms, definition semantics and runtime copies may not. The layout route derives endpoint node IDs from the stored edge and writes an audit event.
- Publish records `definition_hash`, `published_at`, and `published_by` together with its audit event in one fail-closed transaction; project runtime starts only from an exact published revision.
- `pipeline_runs.engine_version` and `pipeline_runs.template_definition_hash` snapshot the selected execution contract and are not refreshed from later revisions.
- Engine v2 run steps snapshot `form_required` and exact `form_version_id`; a submitted different form or synthetic legacy checklist cannot satisfy the gate.
- Runtime steps are deterministically ordered by `order_index,id`; do not reference a non-existent `pipeline_run_steps.created_at` column in run detail or completion-gate queries.
- UAT for official template automation must invoke stable engine-v2 `domain_action_key` actions through the hard-automation gate; display-name automation is legacy engine-v1 compatibility only.
- Engine v2 work items mutate inside the run's current node by default. An authorized, startable future work item is the sole exception: it may enter execution through the explicit audited early-start contract only when the route from the current node is a deterministic `always` chain, target domain blockers are absent, a mandatory reason and current `start_readiness` snapshot token are supplied, and the actor still satisfies ordinary work-item scope/permission. Conditional/unresolved routes, skipped/cancelled/completed targets and stale snapshots fail closed. Early start updates only the target work item/run step plus activity/audit metadata; it never advances `pipeline_runs.current_node_id`, changes node status, resolves a branch or mutates a published/runtime definition. Once started, ordinary form/evidence/signature/approval/automation/completion and domain gates remain unchanged. Advancing a node still requires all run steps/work items, exact forms, node approval, and mandatory automation events to be ready.
- Linked Work Item/Run Step terminal completion is one transactional invariant. Work Item transitions and decisions update the referenced Run Step and verify the final pair before audit/commit; legacy Run Step submit updates the linked Work Item and runs the same postcondition. A missing referenced step or exactly one `completed` side fails closed and rolls back. This postcondition never advances a Node, changes the run pointer or substitutes for `NodeCompletionIssues`.
- Work-item detail treats backend `start_readiness` and `completion_requirements` as separate authoritative contracts. `start_readiness` lists the deterministic predecessor work items and structural start conditions, supplies `can_bypass` plus a snapshot token, and appears above completion requirements while future content remains read-only. `completion_requirements` alone remains the completion-gate/presentation contract. The UI may map canonical form/checklist/photo/document completion requirements to their existing page-local controls, but it must not infer or conflate start and completion gates. Permission requirements preserve `evidence_requirement_json.required_permission` as the immutable backend gate while display uses joined nullable RBAC metadata.
- Every work item exposes exactly one additive backend-owned `execution_target`. The resolver uses immutable runtime `domain_action_key`, node/step business/type codes, `surface_kind`, form presence and live `business_source.route`; it returns the canonical workspace, safe internal route, action label and `completion_mode`. Unknown legacy records and non-domain approvals fail closed to guarded work-item detail. This presentation contract never authorizes an action, mutates a runtime snapshot or replaces mutation-time permission/completion/domain gates.
