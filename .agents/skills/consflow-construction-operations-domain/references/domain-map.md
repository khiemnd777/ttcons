## Invariants

- Operations remains the canonical construction ledger. A workflow work item may open `/projects/:id/operations?task=...`; the task banner supplies assignment/readiness/completion context only, while daily reports, checks, actions, evidence and variation proposals continue through Operations APIs and existing field/current-node permissions.
- Evidence records remain permissioned and checksum-backed. Storage uses the concurrency-safe provider registry with opaque `external|local|s3` provider/key metadata; V70 preserves the external-null-key contract while allowing opaque keys for local/S3 objects. V71 adds a `NOT VALID` future-write check requiring local/S3 keys to be non-null, nonblank and equal to `btrim(storage_key)`; legacy invalid rows remain queryable for operator inventory and block validation until repaired. Local writes are exclusive and descriptor-relative/no-follow on macOS/Linux. Protected downloads authorize the evidence/work item before opening and streaming the object. Evidence detail is read before transaction commit; only a typed pre-commit failure deletes the new object, while an outcome-unknown commit error preserves it to avoid breaking a committed reference.
- `modules/_shared/EvidenceCapture.tsx` owns the reusable local file queue and real/system camera flow. Its shared `evidenceFileTypes.ts` classifier labels PNG/JPG/JPEG/WebP/GIF as Image, PDF as PDF, DOC/DOCX as Word and XLS/XLSX as Excel; only images become `photo`, while every supported document stays `document`. Operations keeps a compatibility re-export; Acceptance reuses the same client validation but still uploads through the canonical work-item evidence endpoint. All new uploads submit `visibility=internal`, the UI exposes no evidence audience chooser, and backend normalization enforces the same value without rewriting historical rows. The backend independently validates bytes/container before storage, so this broader queue does not change storage, permissions, audit ownership or photo gates.
- When a construction work item uses the shared `EvidencePanel`, its work-item evidence uploader exposes up to 10 rows, limits requests to three concurrent calls and keeps per-file/overall progress plus independent retry after partial failure. This does not replace the separate Operations report `EvidenceCapture` queue and does not change construction report linking, evidence ownership, photo eligibility or the one-file backend endpoint.
- Site daily reports preserve did/will, crew, actual quantity, material usage, and photo evidence when present.
- The project construction UI at `/projects/:id/operations` is purpose-first: `Nhật ký`, `Kiểm tra`, and `Cần xử lý`. It must not expose ITP/RFI/NCR/rework/replanning forms in the primary field flow.
- V62 makes the simplified model canonical for field interaction. A check snapshots zero to 30 criteria entered directly in its create/edit dialog; selecting a template only preloads editable rows and never remains a prerequisite. V64 associates up to 10 same-project/work-item, non-rejected evidence records per `context` or `result` role. Completion requires `pass|fail`, at least one result record and an optional note; the first result also remains in `construction_checks.evidence_id` for compatibility. A failed check atomically creates exactly one action from that primary result; manual actions use the same path.
- V65 provides causal traceability from `operation_daily_reports` to field execution. Checks and actions created directly from a report may store an optional `source_daily_report_id`; it must belong to the same project and, when the report has a work item, that same work item. A failed-check action does not duplicate the report foreign key: it inherits the source through immutable `source_check_id`, and workspace reads expose the normalized report ID/link kind. Never infer or backfill this relation from matching dates or work items.
- V66 makes Planning handoff the planned-execution source. One activated snapshot revision atomically/idempotently creates exactly one `construction_handoff_item`, target construction-node `work_item` and canonical `construction_check` per dedicated inspection item. The same submitted form revision always replays its existing handoff. A newer source-form revision may cancel and replace only rows whose work has not started and whose check has no evidence/action; once execution starts, the revision is rejected. Generated checks expose their plan revision, are read-only except through this guarded revision path, and cannot be performed while their generated work item remains `pending`. Pass completes the work item; fail blocks it and the failed-check action must be verified pass before completion. Manual checks remain the path for unplanned field conditions.
- Rev8 combines the planning meeting and QA checklist into one immutable execution-plan form, followed by the existing `construction.activate_handoff` step. Construction execution remains one continuous reporting work package owned by Giám sát; daily reports, generated checks, actions, evidence, NCR/rework compatibility and handover blockers stay in their canonical ledgers.
- Construction workflow `other` handling is exact: `builtin_construction_daily_report.construction_scope|weather` and the two registered subcontractor `work_package` selects may store trimmed same-key custom text capped at 300 characters after draft. A material row whose `source=other` must use its existing `note` before submit/amend; no extra nested payload key is invented. The daily-report bridge preserves those values in workflow answers, the operations snapshot and generated action metadata without creating a stock movement. Blocker `impact=other` remains a catalog classification with no new detail requirement.
- Check edit is limited to pending records created in the simplified model; RFI-backed checks remain read-only and must be changed at their QA/QC source. Action edit is limited to open canonical actions; technical NCR/legacy issue backfills remain read-only. Action source, work item, evidence, impact and status are immutable, while title/description/priority/assignee/due date synchronize to linked issue/rework records transactionally and emit audit.
- Actions transition `open -> waiting_confirmation -> done`. Verification failure returns to `open` and increments `retry_count`; events preserve every resolution/verification attempt. `impact_scope` is one flag and may create a hidden technical replanning link.
- `construction_action_events` remains the source of truth for every remediation submission and verification attempt. Report detail may summarize that timeline, but must open the canonical action View for the complete khắc phục history and evidence.
- Technical issue/rework/replanning rows remain synchronized compatibility/audit records. They are not additional forms the field user must complete. Open simplified actions are handover blockers independently of technical rows.
- Issue update audit policy is key-sensitive. A request body containing `status` writes the mutation and its one `issue_updated` event atomically and fails closed; a request without `status` persists title/description/severity/assignment metadata first and attempts the same single event best-effort, with a structured audit-failure log. The route and response contract do not change.
- The construction timeline maps structured `completed_items.result=done|partial|blocked`, `next_plan_items`, and `blockers` to Đã làm, Đang làm, Sẽ làm, and Vấn đề. Legacy quick reports encode the same three work groups in `work_summary` and must remain readable; an issue record is still distinct from a report blocker.
- Direct construction report create/update is a typed operations command, not a workflow transition. It requires one nonterminal `report_eligible` construction work item and at least one same-project/work-item, non-rejected evidence record whose `evidence_type=photo`; supported PDF/Word/Excel uploads remain `document` and cannot satisfy this gate. Up to 50 evidence records may be linked. Engine-v2+ projects require the work item to belong to the active `construction_execution` node or `construction.item_reporting` step. No-run legacy projects retain the structural work-item/photo gate without a pipeline-node dependency. Update preserves project/reporter identity and emits audit; historical noncompliant rows remain readable through `runtime_compliant=false`. V106 additionally marks pre-lifecycle sources `report_delivery_eligible=false`; they remain readable but reject update/evidence upload. A new eligible source is editable before first formal send, locked during `submitted` and after `acknowledged`, and reopened only by `needs_changes`.
- The manual report create UI is one field flow rather than a sequence of screens: required report context and work groups stay primary, resource/note fields use progressive disclosure, each blocker may remain informational or prepare one check/action draft, and one save first persists the report/evidence then calls the existing canonical V65 create commands. Successful child drafts are never retried; partial child failures keep the saved report and only failed drafts reopen in the same report detail dialog. Existing report detail uses the same compact composer and refreshes linked history in place without changing tabs.
- The construction-report UI labels the mandatory source as `Hạng mục thi công`, filters to server `report_eligible=true`, labels its daily did/current/next group `Công việc trong ngày`, and uploads queued evidence to the work item before posting the report so backend photo validation is atomic with report creation. Queued photo previews own object URLs inside effects so React StrictMode cleanup cannot leave a revoked URL mounted. Stored local/S3 evidence in both the gallery and report form uses the same record-aware `EvidenceRecordViewerDialog` composition over the shared modal shell: photos keep the dark authenticated preview; protected PDF, DOCX and XLSX load on demand through the authenticated endpoint. PDF renders from a lifecycle-scoped blob URL, DOCX renders sanitized content with altChunk disabled, and XLSX parses in a dedicated worker into a bounded read-only sheet grid without executing formulas or hyperlinks. Legacy DOC/XLS, external Office/PDF and other documents keep the light file-first surface. Shared gallery/report options expose only the media-specific `Xem ảnh`, `Xem PDF`, `Xem Word`, `Xem Excel` or `Mở tệp` action and keep the record body as the detail-dialog trigger, without a duplicate `Chi tiết` button. Media MIME/filename classification takes precedence over a stale photo business type, so Office/PDF records never enter the image decoder. Persisted status, source and sender/reviewer audit context remain visible, technical storage/checksum metadata defaults collapsed, and review controls remain permission/state gated. Queued photos use the matching draft composition with an explicit `Chưa upload` state and never fabricate persisted sender/storage/checksum fields. Closing the nested viewer revokes any protected object URL, terminates any spreadsheet worker and preserves the report draft. Progressive `Thông tin bổ sung` keeps crew and material as separate full-width inline-edit tables stacked in one column above field notes. Persistence continues to use `work_item_id` and normal work-item evidence semantics.
- The specialized create/edit dialog and detail use the same hierarchy and frontend read/edit model. Structured blocked completed items plus structured `blockers` are the blocker truth in the red card; legacy/free-text `issues_summary` remains a neutral field note so informational statements such as “Không có sự cố an toàn” are not presented as active blockers.
- Existing linked report evidence is selected through the permission-scoped project evidence read. New files and real-camera captures may be queued before a source is selected, but saving uploads requires the source. `/daily-reports/:id/evidence/upload` delegates storage and permission checks to the existing work-item evidence flow, then links the resulting evidence to the report; there is no project-level evidence storage. Manual detail supports edit and evidence-only quick add, always renders `Minh chứng · N`, and workflow-form-backed reports reject direct update/upload so the source form remains authoritative.
- Submitted `builtin_construction_daily_report` forms are idempotently bridged into `operation_daily_reports` by `workflow_form_instance_id`; the ledger preserves its source work item, structured answer snapshot, primary evidence, progress, crew, material, and issue summaries. A later workflow-form amendment locks and resyncs the same source only before first formal delivery or after the formal recipient requests changes; it rejects historical, submitted and acknowledged sources. Formal send/review remains a `work_reports` overlay and never edits the construction content or earlier revision snapshot.
- `/reports` is the authored delivery register for these source rows. `mine` shows the author, `review` shows only reports addressed to the actor and `all` requires `work_report.manage`; direct detail/export additionally requires author, recipient or project-scoped manager identity. Submit creates revision 1, resubmit requires `needs_changes`, and acknowledgement does not represent acceptance/quality approval or work-item completion.
- Recurring construction occurrences are generated idempotently per plan/date; complete/skip actions require the configured evidence gate and preserve actor/audit history.
- Staff soft-delete never rewrites construction history or clears ownership foreign keys. Daily/work-report, evidence, activity, check and action actors retain their names plus companion deletion flags; open action, active recurring plan/occurrence and activated Planning handoff assignees additionally show `Cần phân công lại`. These live references are authoritative preview warnings, not deletion blockers, and their existing edit/reassignment permissions and construction transitions remain unchanged.
- Field checklist form flows remain separate from reconciliation and final acceptance workflows.
- Work item actions preserve actor, comments, status, and activity history.

## Rev3 Field Ownership And Variations

- Rev3 construction reporting remains the existing per-work-item checklist/photo/daily-report flow owned by `Giám sát`; it does not create a parallel reporting ledger. QA/QC is separately responsible for the client quality dossier in planning/acceptance surfaces.
- Rev4 `...023` makes that separation explicit in the template definition: `construction.item_reporting` is assigned only to `Giám sát` and requires checklist plus photo evidence. This changes future-run responsibility/evidence gates only and does not create a second reporting table or rewrite historical runtime steps.
- Rev7 removes the manually entered daily `progress_percent`, duplicate overview-photo reference and confirmation checkbox from the construction report form. Work-item progress/evidence and the form submit audit remain authoritative; `construction.activate_handoff` now participates in the official-family hard gate and requires an activated `construction_handoffs` source record.
- V88 makes the construction workspace stage-aware: `runtime.construction_active` and per-item `report_eligible` disable new reports/checks/actions before Node Thi công while preserving view/history and later remediation resolution. The check-list filter exposes only eligible items plus sources referenced by existing checks, keeping historical checks filterable without showing future workflow items. Action impact selection is a technical classification only; it never creates a commercial proposal. Action rows expose a linked variation code with a shared Vietnamese status label without treating commercial approval as technical resolution.
- `Phát sinh ngoài kế hoạch` uses the narrow `contract.variation.propose` permission for Admin/PM/Supervisor. `POST /projects/:id/construction-variation-proposals` requires an eligible source work item, optionally locks a same-work-item impacted construction action, creates append-only variation/audit history and atomically enters `qs_review`. Supervisor does not receive broad `contract.view|create`; the path cannot create procurement or bypass QS/Purchasing/PM-Director. Urgent/normal is scheduling only.
- Rev4 Operations UAT uses project `...024` as the read-only pre-construction lock control and project `...025` as the synthetic active-construction sandbox. Only 025 may receive valid test reports/checks/actions/variation proposals; its single eligible reporting item and active client contract are fixture prerequisites, not proof of upstream planning or contract execution.
- Construction variation `amount_delta` is a signed monetary input and uses shared `CurrencyInput` with negative values explicitly enabled; `days_delta`, progress, worker counts, work hours and material quantities remain ordinary numbers.
