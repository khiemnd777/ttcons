## Mandatory Backend Workflow

1. Start in `backend/internal/core/routes.go` bootstrap plus bounded `backend/internal/core/routes_*.go` registrars to confirm the API path and handler.
2. Read the handler in `backend/internal/core/handlers.go` foundation plus bounded `backend/internal/core/handlers_*.go` owners for request parsing, actor extraction, response envelope, and service call.
3. Read the matching bounded service file in `backend/internal/core/service_*.go` for validation, permission checks, normalization, file handling, and domain transition orchestration. `service.go` now owns only the `Service` container, constructor, runtime configuration, and shared limits.
4. Read repository functions in `backend/internal/core/repository_domain.go` foundation plus bounded `backend/internal/core/repository_*.go` owners or generic helpers in `backend/internal/core/repository.go` for SQL and state persistence.
5. Check request/response structs in `backend/internal/core/types.go` foundation plus bounded `backend/internal/core/types_*.go` contracts.
6. Check immutable ordered migrations and additive seed.sql master data; validate_current_seed.sql / make seed-validate is the current gate. Runtime sample v5 generates current published sources; never reapply V41/reset revisions or removed Golden runtime SQL.
7. Update this map or the central map when adding, renaming, moving, or deleting backend routes/functions/helpers.

- After validation, scope, permission and active-node checks, the first successful draft save or submit atomically transitions the linked active Work Item `ready|needs_changes -> in_progress`, sets `started_at`, synchronizes the run step and writes exactly one source-tagged `started` activity/audit in the same transaction. - Unstarted future work remains behind the explicit reason/snapshot-token early-start contract. Routes, payloads, schema, published definitions and historical rows are unchanged.

## Cross-Module Work Item Start On Successful Mutation

- Shared owner: `work_item_domain_start.go` (`WorkItemMutationContext`, module policies, `startWorkItemForDomainMutationTx`, `attachWorkItemTransition`); request contracts live in `types.go` foundation plus bounded `types_*.go` contracts and `types_project_finance.go`.
- The helper locks Work Item and engine-v2+ Pipeline Run, loads the linked Pipeline Run Step `surface_kind` and `domain_action_key` as persisted execution context, verifies project, domain action/workspace policy, `CanActOnWorkItem`, required project permission, schedule, active current Node and startable status, then reuses `persistWorkItemStartedTx`. The source record and transition commit or roll back together. `in_progress|blocked` are no-op transitions; terminal/future/mismatched contexts fail closed. Responses add `work_item_transition`; ordinary calls without context remain unchanged.
- DB-backed module regression fixtures must bind the Work Item to a current Pipeline Run/Node/Step with the exact surface/action under test; a generic unbound `issue/task` intentionally resolves to the fallback `work_item` workspace and must not be used to bypass module policy.
- First searches: `rg -n "WorkItemMutationContext|startWorkItemForDomainMutationTx|attachWorkItemTransition|work_item_transition" backend/internal/core` and `rg -n "withWorkItemMutationContext|syncWorkItemMutationTransition" frontend/src/modules`.
