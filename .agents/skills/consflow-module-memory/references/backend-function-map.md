# Consflow Backend Function Map

Use this map after `module-keyword-map.md` for backend/API/schema/function work. This is a routing cache for fast ownership discovery, not a substitute for reading code.

## Mandatory Backend Workflow

1. Start in `backend/internal/core/routes.go` to confirm the API path and handler.
2. Read the handler in `backend/internal/core/handlers.go` for request parsing, actor extraction, response envelope, and service call.
3. Read the matching service in `backend/internal/core/service.go` for validation, permission checks, normalization, file handling, and domain transition orchestration.
4. Read repository functions in `backend/internal/core/repository_domain.go` or generic helpers in `backend/internal/core/repository.go` for SQL and state persistence.
5. Check request/response structs in `backend/internal/core/types.go`.
6. Check migrations in `backend/migrations` and seed data in `backend/seed/seed.sql` when tables, statuses, permissions, defaults, indexes, or demo data are involved. Full-product review data additionally lives in `backend/seed/golden_project*.sql`, `backend/seed/golden_live_project.sql`, and the versioned `backend/seed/golden_client_workflow_rev*.sql` fixtures; it is guarded by `backend/seed/validate_golden_project.sql` / `make seed-validate`. `backend/Makefile` reapplies V41 before the later reference-data migrations, then restores V92/V102/V103/V104/V105 and adds the version-specific Golden runtime fixtures before validation.
7. Update this map or the central map when adding, renaming, moving, or deleting backend routes/functions/helpers.

## Golden Sample UAT

- Golden completed fixtures are read-only. `GOLDEN-LIVE-001` remains the legacy isolated walkthrough; Rev4 review uses entry control `GOLDEN-REV4-ENTRY-001` read-only and permits valid Operations UAT records only on synthetic construction fixture `GOLDEN-REV4-CONSTRUCTION-001`.
- Rev4 projects `...024` and `...025` both snapshot published template `...023` at engine 3. Project 024 is a production-shaped `project_intake` state. Project 025 deliberately places only `construction.item_reporting` in `ready`, keeps every other node pending, and includes one active main-client receivable contract; it is UX test data, not evidence that upstream workflow gates ran.
- `GOLDEN-REV6-LEAN-001` (project/run `...026`) snapshots published Rev6 `...025` at engine 4 after a valid `survey_required` intake transition: intake is completed, Survey is current with six ready work items, 44 later work items are pending, and its 50 exact form instances include 43 immutable `lean_capture_v2` references. The seed file is additive/idempotent and never rebinds Batch3 or older Golden runtimes.
- Use [Golden Sample role-based UAT](../../../../docs/operations/golden-sample-role-based-uat.md) for the DB/reset guard, 15-role J0-J9 matrix, evidence contract, pass/fail criteria and explicit browser authorization gate; use `backend/seed/GOLDEN_LIVE_RUNBOOK.md` for the node-by-node business scenario.
- Official planning steps that assign PM and require `planning.edit` depend on the additive PM grant in V72; `CanActOnWorkItem` still enforces project membership and role assignment before `requireWorkItemPermission` checks the permission key. `backend/internal/shared/migrations/official_workflow_actor_permissions_test.go` verifies the migration grant for an existing PM role, while `backend/seed/validate_golden_project.sql` verifies seed parity and the 14-member App-only Golden Live fixture.
