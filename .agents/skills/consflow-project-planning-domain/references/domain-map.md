## Invariants

- Planning reports are project-scoped and permission-filtered.
- A newly created/imported real project with non-null `projects.created_by` has a server-derived startup projection until its first Pipeline Run exists. Manual create and My Work resume use the same three-step `ProjectStartupWizard`: metadata first, then Staff membership, then PM/readiness setup. Completed steps are backward-navigable only under the exact server capability: Step 1 requires project-scoped `project.update`, Step 2 requires member management. A resumed Step 1 reloads the current project and shared partner/Published-Pipeline catalogs, saves through the existing guarded project update, refreshes readiness and preserves unsaved member drafts. The Staff step saves 1–50 unique new/reactivated members atomically with per-member audit and keeps existing active memberships locked; it cannot advance until every selected member has operational roles and `project.view`, and at least one active/selected member's role union grants `project.view`, `project.member.manage` and `pipeline.run`. Setup presents the complete saved active membership list separately from a whole-template operational-role coverage projection derived from the selected published revision. Only active App accounts cover a role; every coverage `members` field is a JSON array and the frontend defensively normalizes legacy `null`; missing later-template roles remain informational and do not change readiness. Creator is the temporary owner; an active linked PM member becomes owner after the audited dedicated handover. `/my-work` shows owner action and eligible first-step preview without creating fake Work Items. A `setup_required` projection contributes to the actor/project-scoped `Làm ngay` count only for `responsible` and `all`; it never contributes to backend direct, department or watching Work Item scopes. Direct assignment is already included in `responsible`; the compatibility-only `mine` scope is not a separate My Work UI choice. Pipeline start for this cohort fails closed unless the effective template is published, PM is active and each first-node step has at least one active member matching operational role labels and required permission. Sample and legacy null-creator projects keep their historical compatibility. Successful start resolves the setup thread, creates runtime Work Items and emits exact-role assignment notifications.
- Project XLSX/JSON import is a project-master setup action, not runtime orchestration. Readiness/template/preview/execute require a ready published Pipeline catalog plus published active Workflow Form versions containing Fields. XLSX and `consflow.project-package` JSON v1 adapt to the same exact nine-field canonical request, capped at 100 rows/5 MB; authoritative preview rejects duplicate/existing project codes and stale Pipeline/partner references and HMAC-binds format/version. Execute revalidates and atomically writes only draft `projects` with selected `pipeline_template_id`, zero contract/progress, per-project/batch audit and same-actor idempotent batch metadata including `source_format`. It never starts Pipeline or creates runtime nodes/steps, work items, form instances/answers, members or domain records. Export uses current scoped non-cancelled filter/sort or max-100 selection, remains available when reference data is incomplete and records selected/runtime reference state in the XLSX workbook or nested JSON snapshot; money in JSON uses exact decimal strings.
- Workflow Definition XLSX/JSON can bootstrap Form/Fields and Pipeline definitions when the system has no published catalog, but import always produces drafts. Those drafts deliberately do not satisfy Project import readiness; an authorized reviewer must separately publish valid Form versions and Pipeline revisions before Project template download/import becomes available. Workflow Definition export stays independent of the Project readiness blocker.
- The operational project report counts open issues and pending approvals in independent correlated subqueries per accessible non-cancelled project; it must not join both one-to-many sources before counting. Optional `project_id` and CSV export retain the same scope.
- Meeting minutes action items and daily report next-plan outputs remain traceable.
- Planning checklist evidence/status summaries do not replace the underlying submitted form history.
- The survey-stage `client_site_risk_assessment` keeps fast capture as its primary purpose: `risk_items.category` is hidden from UI/new-PDF presentation and a missing value is normalized to stored `other`; explicit historical categories, published form definitions, existing PDF artifacts and downstream workflow gates are not rewritten.
- The Survey work-package form keeps `dimension_items` as a required non-empty list, with required `dimension` and `unit`, while exact nested `area` is optional and accepts blank or 1–160 characters through an effective frontend/backend compatibility rule. Drafts may retain below-minimum text in other fields; submit/amend still enforces published minimums. Published definitions, current/historical runtime references, stored answers, PDF artifacts and planning transitions are never rewritten.
- Planning workflow selects participate only through exact registry entries: `client_design_style_brief.style_direction`, `client_survey_work_package.style_direction`, `builtin_daily_report.planning_scope`, and `builtin_checklist.planning_scope`. Their published choices stay immutable; `other` requests inline same-key free text, drafts may retain the sentinel, and submit/amend requires trimmed text capped at 300 characters. Reopening maps the stored custom value back to `Khác` plus text. This does not relax any unregistered planning select or mutate definitions, runtime references, PDF history or planning transitions.
- Project detail and global workspaces must agree on statuses and available actions.
- The project shell is one business tree, not a switch between a workflow tree and business modules. `Kế hoạch` contains `Hồ sơ chuẩn bị`, `Kế hoạch công việc`, and `Quy trình`; BOQ is under `Thương mại & Vật tư`. `ProjectTaskContext` accepts presentation-only `?task=<workItemId>` on canonical domain pages, while authorization and mutation remain with the existing work-item/source-domain endpoints. Work-item detail routes remain guarded compatibility and completion surfaces.
- `Hồ sơ chuẩn bị` is a single-focus planning workspace. Its route without `?task=` gives the actionable queue the full content width and defaults to `Cần xử lý`; upcoming, completed and all history stay explicitly discoverable. Filtered/search-matching rows preserve workflow order inside collapsible `Giai đoạn <tên>` sections that start expanded; stage ordinals and repeated per-row stage labels are omitted on desktop/mobile while step ordinals remain. A selected `?task=` replaces that queue with the full-width guarded Work Item workspace and resets document scroll to the detail header, so the Work Item form/action layout is never compressed by a persistent preparation rail and mobile navigation never lands below its return control. Above the unchanged work title, a compact toolbar shows only `Giai đoạn <tên>`, `Bước x/y`, previous/next within the same pipeline-run node and `Tiến độ`; previous/next use each sibling's canonical `execution_target`, never cross into another node and never infer graph branches. The toolbar replaces the technical Node/Bước breadcrumb and must not become a tall three-card mini-workflow. In the project tree, an expanded group remains a neutral navigation heading and only its exact child route receives the strong active treatment.
- Global `/progress` is a standalone project-stage board, not a tab inside `/projects` or project detail. It is read-only and gated by `project.view`; cards navigate to project detail and never drag/drop or transition runtime state. Summary and cursor-stage queries exclude cancelled projects through `ProjectAccessFilter`, join only the project's snapshotted `current_pipeline_run_id` and that run's `current_node_id`, and share the same SQL mapping of technical node types into stable presentation stages. Projects without a run remain `Chưa khởi động`; completed runs remain `Hoàn tất`; unknown/custom types remain visible in `Khác`. Search, PM UUID and project status are server-authoritative; a stage page defaults to 25/max 50 and binds its descending `created_at,id` cursor to stage plus normalized filter hash. Blocked/overdue/issues/pending approvals remain independent badges calculated only for returned page IDs. The legacy full endpoint stays temporarily for rolling compatibility, while the page consumes only summary/stage. Frontend keys are actor-scoped, desktop loads visible/near columns, mobile loads one selected stage, card lists virtualize and deep pagination is refreshed only by an explicit cursor reset. The 10k/80%-skew gate passed, so no progress-specific index, migration or Redis response cache exists.
- Project Thành viên uses a dedicated typed API rather than the Operations payload. Active App members with `project.view` see active membership; `project.member.manage` controls inactive history and mutations. Single and bulk save/reactivate synchronize `project_members` with project-scoped `user_roles` transactionally, keep global roles untouched and audit every member; bulk is one all-or-nothing transaction with one post-commit work-queue invalidation. Deactivation stays in the full Member workspace, soft-deactivates history and protects the current PM from removal; the startup wizard never deactivates or unchecks saved active members. External-only users, role IDs and matching operational labels are excluded from options and rejected on save; V89 soft-deactivates existing linked client memberships without deleting history.
- Project-member responses expose additive `account_active` from the linked active User plus Staff state. Startup keeps every saved active membership visible and locked, but only account-active linked members count toward viable membership and PM eligibility; backend PM assignment repeats the active account check authoritatively.
- `Kế hoạch công việc` is an action-first queue over every ordered runtime step. Its default `Cần xử lý` view is derived from work-item runtime status, `waiting_approval`/`waiting_review` stay distinct, only `pending` is future work, and terminal/skipped work remains discoverable outside the actionable queue. The one next-work CTA stays blocker -> waiting approval/review -> other open work. Rows navigate through the server `execution_target`; embedded form/evidence/approval targets additionally carry a work-item-scoped, one-time router-state intent so an explicit CTA opens the sole shared `ProjectTaskContext` dialog. Plain `?task=` deep links remain context-only, and return destinations exclude stale `task`/`returnTo`. Node approval/block controls and the full transition history remain in `Quy trình`; a ready, authorized current-Node advance is additionally projected into personal My Work so routine users need not navigate there merely to continue the workflow.
- Official workflow revision 2 separates `Kế hoạch thi công` from field `Thi công`. The dedicated `client_construction_handoff_plan` form owns the inspection-item list; Planning exposes one bulk review/activation CTA. Every new/revised inspection item requires at least one result photo or document: the legacy `evidence_required` key remains in published/request/DB shapes for compatibility, but exact-form UI/PDF presentation hides it and form save/submit plus activation force `true`. Existing activated snapshots and construction history are not backfilled. The planning node cannot complete until a handoff snapshot is activated. Each activation preserves source form/node, actor/time, form revision, handoff revision and hash; the request carries the previewed form revision and stale-tab activation is rejected after a locked recheck. Replaying the same submitted form revision returns the existing handoff. A newer form revision may supersede only generated rows that are still unstarted and have no evidence/action; otherwise activation is rejected so field history is never overwritten. Current revision-1 construction runs may import submitted QA/assignment data without mutating their runtime history.
- Project Tổng quan leads with one prioritized action ordered blocker -> waiting approval/review -> other open work, shows the current runtime stage beside it, keeps source-backed attention counts separate from budget/contract/schedule reference data, and uses Vietnamese system labels without translating user-entered project/work-item data.
- Project Hồ sơ is a project-scoped work-item evidence workspace: summary/search/filter/cursor results use the same visibility and work-item scope, waiting review sorts first, rejected evidence remains discoverable as history, cancelled-work-item evidence stays excluded, and review controls appear only when backend `CanDecideWorkItem` yields `can_review=true`. Its list keeps the blank action track first, then presents `Hồ sơ`, `Giai đoạn` (`run_node_name`) and `Đầu việc` (`work_item_title`) as explicit columns at `xl`; below `xl` the same values remain labelled in stacked rows. Long file/source/sender text truncates with ellipsis and exposes its complete value through a native hover tooltip; standalone source/sender values are focusable with a complete accessible label, and missing historical values show `—`. The action track exposes only the media-specific `Xem ảnh`, `Xem PDF`, `Xem Word`, `Xem Excel` or `Mở tệp`; clicking the file cell remains the canonical detail-dialog entry, so there is no separate `Chi tiết` button. Its canonical detail dialog is media-aware: an image remains viewable in-app; protected local/S3 PDF, DOCX and XLSX load on demand through the authenticated evidence endpoint. PDF renders from a lifecycle-scoped blob URL, Word renders sanitized HTML with altChunk disabled, and Excel parses in a dedicated worker into bounded read-only sheet tabs/virtualized rows without executing formulas or hyperlinks. Legacy DOC/XLS, external Office/PDF and other documents remain file-first. Media MIME/filename classification takes precedence over a stale photo business type. Source/sender/reviewer context stays grouped for quick verification, storage/original-name/SHA details remain under a collapsed technical disclosure, and document presentation does not change project evidence permissions or review transitions.
- Project activity defaults to all visible activity and uses total visible count for the project-tab badge; attention counts remain inside `Cần chú ý`, and the `Quyết định` tab uses the dedicated source-backed `decisions` summary count. It uses server-backed search/filter/cursor pagination and permission-scoped picker options. Resolving a question, blocker, or reminder preserves history by appending a system event and audit record.
- Project, global-progress and personal-attention SSE are invalidation-only. Project streams emit only event type, project ID and timestamp after the initial authoritative project check. The global progress stream snapshots `ProjectAccessFilter`-visible project IDs once, maps direct work-item changes plus explicit project/runtime/issue/approval mutations to minimal `project_progress_changed`, and permits a project-agnostic create invalidation without exposing a new project ID; disconnected clients poll the authoritative snapshot every 60 seconds. Personal attention builds the actor's operations-visible project-ID snapshot once when the connection opens and filters in memory, avoiding per-event/per-subscriber DB amplification. Connections consume bounded process/IP/actor capacity, release it idempotently and close at a randomized 80-100% of the configured maximum lifetime (default about four to five minutes); reconnect rebuilds JWT/session/project visibility so revocation lag is bounded without a synchronized reconnect herd. Multi-replica fanout uses Redis Pub/Sub with source-instance deduplication, and Redis outage degrades to replica-local delivery.
- Personal attention summary and detail share the same project/role/work-item/client visibility contract. Summary probes only the first 121 attention candidates and caps the badge at `120+`; detail limits candidates before enriching attachments, conversation, reactions, mentions and target labels. Both are read-only with transaction-local JIT disabled, and the UI only requests detail while its tab is active. These performance boundaries never broaden project visibility or change activity resolution/read semantics.
- Project `Nhật ký` is a five-event preview backed by the paginated project Audit endpoint; the tab does not treat the preview length as the total and routes full investigation to `/projects/:id/audit`.
- Project `Thảo luận` presents activity as chronological chat with a persistent composer and scroll anchoring. A reply is a new `comment` row linked by `parent_activity_id`; backend copies the parent project/target/work item/visibility and auto-mentions its actor. Reactions use `activity_reactions` active-state upserts, are visibility-gated, and never change read/resolution/workflow status or activity totals. Only the author may edit or withdraw a `comment` during the first 15 minutes; edits/withdrawals append `activity_message_revisions` and audit, withdrawal clears current content/attention/reactions but keeps a tombstone and existing replies. Typed operational activity is immutable.
- Project `Quy trình` is the runtime coordination/history surface: default to all node work items, keep completed and skipped records discoverable with filters, render skipped work read-only, and keep dependency/approval/node actions backend-gated. It is not a parallel business editor; work rows open the canonical source workspace.
- The expanded `/projects` explorer and the project workspace sidebar share one group/child/permission route config. A group landing resolves to its first visible child, with its own target as fallback. Explorer search, status, global sort/direction and page-size 25/50/100 are server-authoritative through `/projects/explorer`; the query key is actor-scoped and a page displays only its returned records. Expansion remains project-ID based and user-controlled: every loaded page starts collapsed, authoritative refetches retain only manually expanded IDs that are still visible, and a search/filter/page change with no retained ID does not open the new first row. The invalidation-only stream refreshes the current authoritative query and a disconnected client polls every 60 seconds. On narrow screens each top-level project and optional expanded workspace remain one bordered rounded card; desktop retains dense rows and the 58/42 folder/dashboard layout.
- Project deletion is a scoped soft-cancel transition. The explorer exposes selection only to actors carrying `project.delete`, clears it on search/filter/sort/page/page-size changes and caps execution at the visible page/max 100. Backend checks `project.delete` plus project scope for every UUID before revealing preview data, binds current status/update time and workflow/work/issue/finance/stock/acceptance impacts to an actor-keyed HMAC, then locks and changes every selected `projects.status` to `cancelled` atomically. It never deletes runtime, finance, stock, acceptance or history rows. Per-project and batch audit are fail-closed, V116 stores same-actor idempotent replay, and successful commit invalidates progress/explorer state. The legacy single `DELETE /projects/:id` remains compatible but uses the same audited soft-cancel semantics.
- Project explorer Redis is a disposable acceleration layer, never an authorization source. The index key includes catalog and actor scope revisions; each row key includes its project revision. Before serving cached rows, backend re-applies `ProjectAccessFilter` and reads project revisions only for IDs currently visible to the actor. Project, derived issue/approval data, membership, staff, role, partner and template writes bump revisions transactionally and enqueue an after-commit SSE invalidation through the durable outbox. Redis outage, corrupt/oversized values, lock contention, circuit-open or scope mismatch falls back to PostgreSQL without changing the response contract.
- Soft-deleting a Staff project manager never clears `projects.pm_staff_id`. Project list/explorer/workspace/detail/progress responses keep `pm_name`, add `pm_account_deleted`, display the deleted-account suffix and mark live ownership `Cần phân công lại`. The deletion transaction touches the project revision so Explorer cache/SSE cannot retain an active-looking PM. Deleted memberships are inactive history and remain visible only through the authorized inactive-member view; active member/PM selectors exclude them.

- Project metadata review/edit on `/projects` has one pencil entry point. Its unified dialog presents the current status, progress and partner snapshot/tax as read-only context above the editable metadata/template form; no separate eye/detail action or additional detail request exists, and the project-workspace folder action remains separate. The selector is labelled `Chọn chủ đầu tư có sẵn`, the read-only summary is `Chủ đầu tư đã chọn`, and the helper describes storing the current name in plain language.

## Notification Platform Boundary

- V127 enables `activity.mentioned`: resolved user/role mentions first persist in `activity_mentions` and read-state rows, then the same activity transaction emits one explicit-user notification event. The projector rechecks active internal account and current project scope; role resolution never broadcasts to same-named roles outside the project.
