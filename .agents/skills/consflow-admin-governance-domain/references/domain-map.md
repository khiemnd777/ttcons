## Routes

- Auth, personal profile and account recovery: existing auth/profile routes plus public `POST /auth/password/forgot`, `POST /auth/password/reset`, `POST /auth/recovery-email/verify`, protected `PUT|DELETE /auth/recovery-email`; product pages `/profile`, `/change-initial-password`, `/forgot-password`, `/reset-password`, `/verify-recovery-email`

- Staff/RBAC: `/staff`, `/roles`, `/permissions`, `/roles/:id/permissions`, `/users/:id/roles`
- Project membership governance: `/projects/:id/members`, `/projects/:id/members/:memberId`
- Business audit/settings: `/audit-logs`, `/projects/:id/audit-logs`, `GET|PUT /settings`, `GET /settings/backup`, `POST /settings/backup/preview|restore`
- Runtime Event Logs: protected `GET /event-logs`, `GET /event-logs/:id`; product page `/event-logs`
- Statistics governance: `/statistics/options`, `/statistics/staff` and `/statistics/staff/export`; authored-report governance: `/work-reports/*`; legacy Dashboard/professional-report routes remain `/reports/*`

## Invariants

- `Bàn làm việc` remains actor-scoped. Backend `execution_target` is a navigation hint produced only after ordinary list/detail scope; frontend accepts internal routes only. The hint never replaces project visibility, work-item action scope, source-module RBAC or mutation-time authorization, and unsafe/missing targets fail closed to guarded work-item detail.
- Protected endpoints stay under auth middleware.
- The shared IP rate limiter runs before JWT/session work. `AuthClaimsRequired` must stop on missing/invalid JWT; only verified claims supply the actor key, so actor rate limiting runs before authoritative `AuthSessionRequired`/`AuthSessionActive` DB validation. Heavy-route concurrency runs after the session gate. Rejected `401`/`429`/`503` requests never reach business/audit handlers; backpressure responses use the shared envelope with `Retry-After`. Trusted proxy CIDRs must identify only the immediate Caddy/internal proxy network.
- Backend permission helpers are the source of truth for authorization.
- Audit read APIs are server-filtered and page-number paginated, return project labels plus permission-scoped filter options, use global `ProjectAccessFilter` or project `requireProjectPermission`, and expose metadata read-only. Audit persistence is centralized in `backend/internal/core/audit.go`: critical governance/workflow/finance and quality approval/terminal mutations use the same DB transaction and fail closed; classified non-critical operational events remain best-effort but emit structured failure logs. Metadata serialization and insert errors must never be silently discarded on a critical transition.
- Event Logs are operational diagnostics, not business audit history. V111 reserves `event_log.view` for Admin/Developer at migration-trigger, repository replacement and seed layers; `audit.view` never implies access. Capture covers final backend unexpected 5xx, panic and controlled backend 503, while excluding 4xx/429, `/metrics`, liveness/readiness and Caddy-only gateway failures. Rows retain at most 90 days and store registered route, request class/ID, known actor/project context, deterministic fingerprint and sanitized diagnostics without request body, query string, auth header/cookie or raw IP. Persistence is best-effort and its failure emits only a secret-safe structured fallback; it must never replace the original response. Full message/stack remain detail-only. Public generic 500 responses and shared frontend 5xx toasts expose the same request ID.
- Activity reply/reaction/edit/withdraw endpoints remain protected and reuse `ActivityVisibleToUser`; edit/withdraw additionally require exact author ownership, activity type `comment`, an unwithdrawn row and the 15-minute server window. UI capability flags never replace backend enforcement, managers receive no override, and no new global permission is introduced.
- Frontend navigation and row actions mirror permissions but do not replace backend enforcement.
- V110 reserves Settings governance by capability and system role: Developer owns `settings.view|settings.update|seal.manage`; Admin retains `settings.view|seal.manage` but cannot receive `settings.update`; other roles cannot receive these reserved Settings/seal-management permissions. V111 separately grants `event_log.view` to Admin/Developer and rejects every other role. The backend role-permission replacement path enforces both boundaries, while frontend visibility is presentation only. Local seed supplies `developer@consflow.local`; migration never creates a production user.
- V112 closes the fresh-production gap without running demo seed. V113 adds Developer-only `staff.import`, removes it from every other role, enforces the restriction with a database trigger and adds no production user. `cmd/bootstrap-admin` remains the only production first-Admin path: its complete Admin grant check excludes the Developer-reserved `settings.update` and `staff.import`, then serializes, bcrypt-creates linked identity/global Admin/audit atomically and no-ops only for the same healthy Admin email.
- System settings use an explicit typed registry, optimistic row versions and fail-closed audit in one transaction. Legacy runtime environment values are imported only when a row is missing, then PostgreSQL is authoritative. Sensitive `SMTP_PASSWORD` has no plaintext JSON value and is AES-GCM encrypted with the core `.env`/secret-file `SETTINGS_ENCRYPTION_KEY`; bootstrap, connection, storage and root-secret fields remain outside the database and read-only in the API/UI.
- Settings JSON backup is a portability aid for database/UI policy only, not a database dump. `settings.view` may export all non-sensitive registry values plus secret configured-state metadata; neither plaintext/ciphertext secrets nor core `.env`, seals, identities or business records enter the document. `settings.update` alone may preview/restore. Preview is no-write; restore recomputes the file hash, checks expected row versions, rejects core/secret/invalid-known payloads, warns and skips unknown compatibility keys, preserves missing/current secret values, and commits all changed known settings plus per-row/summary audit in one transaction. No backup artifact is stored server-side.
- Work-item detail may expose the permission catalog name/description as presentation metadata, but authorization continues to use the raw snapshotted key through backend permission helpers. User-facing requirement text must not reveal raw keys; missing catalog metadata falls back to generic administrator guidance. V96 standardizes `planning.edit` as `Cập nhật kế hoạch` / `Cập nhật nội dung kế hoạch được phân công` without adding or removing any role grant.
- Submitted workflow-form amendment capability is server-owned and combines `CanActOnWorkItem` with the work item's snapshotted required permission; the UI `can_amend` flag only controls presentation. Amendment does not grant managers/directors a new override and does not require the historical work item to remain the current pipeline node. The atomic `workflow_form_amended` audit stores actor, mandatory reason, from/to revision and exact field-label-aware before/after changes; audit failure rolls back the content revision. Later signatures, seals and PDFs remain separately attributable to their form revision.
- My Work is one adaptive actor-scoped role workbench, not one page per role. List/detail `readiness`, capabilities and `available_actions` are actor-specific presentation hints only. `pending_approval` retains requester separation, required decision roles and project scope; `upcoming` work remains visible but current-time/current-node backend gates deny every mutation path. The authenticated SSE still exposes invalidation-only `work_queue_changed`. No new global permission, role filter, manager override, table or migration is introduced.
- Aggregate navigation is labelled `Thống kê`, requires `statistics.view`, and uses `statistics.export` for PDF/Excel/CSV. V106 copies existing `report.view` role grants to both statistics permissions so the former aggregate audience keeps access; `report.view` remains the Dashboard/legacy compatibility gate and does not authorize authored employee reports.
- Authored `Báo cáo` navigation requires `work_report.view`. Field roles carrying `operation.report` receive view/create/submit/export; Admin/Director/PM receive their explicit review/manage subset from V106. Backend checks do not rely on those role names: list scopes require the corresponding permission, every project filter/detail/export combines project permission with `ProjectAccessFilter`/`CanAccessProjectPermission`, and direct report detail/PDF additionally requires author, recipient or project-scoped `work_report.manage`. Review requires recipient identity unless the actor has project-scoped manage.
- `Tài chính công trình` remains separately gated by `project_finance.view`; its management totals/export require `project_finance.report_view`. Legacy `report.finance.view`/`accounting.*` are removed from every non-admin role by V83 and seed parity.
- Staff report is a project-allocation view: only active staff memberships in accessible non-cancelled projects are returned and distinct accessible projects are counted. Full-company staff is available only through the `staff.view` Staff module.
- `project.member.manage` is granted to Admin/Director/PM and always combined with project scope. Project member responses expose server capabilities; mutation synchronizes only project-scoped `user_roles`, never removes global roles, never exposes Admin/Director as assignable project roles, and writes project audit.
- Partner catalog updates preserve downstream snapshots for historical documents.
- Partner management is split into independent `Đầu vào` and `Đầu ra` global navigation entries. Input contains every partner with `client`; output contains every partner with at least one non-client type, so a multi-type partner may appear in both. Output exact-type choices exclude `client`. This presentation and additive query grouping do not rename the shared `/partners` API, `partners` table, `catalog.view|manage` permissions or downstream snapshot fields; `/core-data` remains a compatibility redirect.
- Project setup presents the active `client` partner selector as `Chọn chủ đầu tư có sẵn` and its selected summary as `Chủ đầu tư đã chọn`; these user-facing labels do not change active/type filtering, `partner_id`, name snapshot behavior or catalog governance.
- Session refresh/revoke lifecycle remains DB-backed and revocable.
- Every new password uses one canonical backend/frontend contract: non-whitespace, at least 8 Unicode code points and at most 72 UTF-8 bytes. Self change, recovery reset and Admin replacement require an exact confirmation; only initial Staff account creation intentionally omits confirmation. Replacing an existing account password must differ from its current bcrypt credential. Login and current-password fields validate presence only because they verify an existing credential rather than create one. All account-password UI controls use the shared eye-toggle component; the Staff initial-password suggestion is generated client-side with Web Crypto and never returned by the API or stored in audit metadata.
- Personal Profile is actor-owned and permission-free after authentication: neither self-service mutation accepts a target user ID. `/auth/me` uses `users` for login identity and a preferred non-deleted linked `staff` row for phone/department/position. Profile writes mirror full name/email/phone to every linked non-deleted staff row in one audit-atomic transaction, never create governance staff implicitly, and leave department/position/roles read-only. Email change requires the current password; password change requires current/matching confirmation and persists bcrypt only. Either sensitive change revokes every session and clears the refresh cookie so the JWT email used by later audit cannot remain stale. Audit records changed field names/session outcome only and never password material; historical audit/activity actor snapshots are not rewritten.
- Self-service recovery email is optional, actor-owned, users-only and never mirrored into `staff`. `/auth/me` exposes availability plus masked verified/pending values only. Shared masking exposes at most the first three local-part characters, the first domain character and final suffix (`abcdef@gmail.com` -> `abc***@g**.com`). Self set/replace/remove requires current password; a pending replacement cannot displace the old verified address. Separately, an actor with both `staff.update` and `staff.account_security.manage` may set a linked user's normalized recovery address through `PUT /staff/:id`, and an actor with both `staff.create` and `staff.account_security.manage` may supply it during `POST /staff`; either Admin path marks the address verified immediately without delivery or confirmation. `GET /staff` always exposes `has_recovery_email`, but only an actor with `staff.account_security.manage` receives `recovery_email_masked`; the full repository-only field is removed before the response. Blank Admin edit fields mean unchanged, every recovery address must differ from the actual login email and unlinked staff fail validation. Forgot accepts login email but returns one enumeration-safe response immediately; bounded background delivery sends only for active non-external accounts with a verified recovery address. Verification lasts 24h by default and reset lasts 15m by default; raw 256-bit tokens exist only in memory/email URL fragments while PostgreSQL stores SHA-256 hashes. Consumption rechecks active/non-external/verified-target state, is one-time and audit-atomic. Self reset or Admin password reset bcrypt-updates the password and revokes every target session; either Admin security change invalidates active recovery tokens. Audit/logs never contain password material, raw tokens or full recovery addresses; local `.local` seed accounts receive no recovery address.
- Staff account creation and security administration are governance actions, not recovery-delivery actions. `POST /staff` requires both `staff.create` and `staff.account_security.manage`, takes one initial password with no confirmation plus an optional recovery email, and creates the linked `users` and `staff` rows with two fail-closed audits in one transaction. Staff department and position are optional profile metadata, not authorization: whitespace-only values normalize to SQL `NULL`, explicit blank edits clear them, and omitting either update key preserves it. An absent department cannot satisfy department-only work routing until updated; role/staff/project assignment remains independent. No role is assigned implicitly; the independent shield action remains authoritative. `PUT /staff/:id` always requires `staff.update`; nonblank `new_password`/confirmation/recovery email additionally requires `staff.account_security.manage`. Staff edits reject direct user relinking, synchronize normalized full name/login email to the user and all linked non-deleted Staff rows, derive user active state from linked Staff rows and reject activation of an external-only account. Password, login-email or activation changes revoke target sessions; password and recovery changes invalidate active recovery tokens. A self-sensitive update returns `reauth_required` so the frontend clears its session. The Staff edit dialog uses one pencil and one combined form, keeps the replacement email input empty, shows the permission-scoped current mask as helper text and awaits authoritative refetch after a non-self save. Role/project replacement semantics remain unchanged.
- Bulk Staff account import is a separate Developer governance action. Both preview and execute require `staff.import`, `staff.create`, `staff.account_security.manage` and `permission.assign`. The browser accepts exact 8-column `.xlsx`/`.csv` up to 1 MB/100 rows and sends structured rows; backend preview remains authoritative. Execute binds rows to a server-keyed HMAC plus UUID idempotency key, revalidates and atomically creates active User/Staff, optional immediately verified recovery email, exactly one non-external/non-Admin/non-Client/non-Developer global role, batch record and secret-safe audits. The source file, password and recovery address are never stored in the batch/audit. Imported users carry `must_change_password`; DB-backed middleware permits only `/auth/me` and own password change until successful self-change or recovery reset clears the flag and revokes sessions.
- Account recovery is opt-in and operationally isolated. `AUTH_RECOVERY_ENABLED=true` plus a frontend origin activates the normal UI/API contract in development/test even when SMTP is missing or invalid: startup selects a non-delivering preview sender, logs only `provider=preview delivery=discarded`, persists ordinary pending/token state and never logs raw tokens or full recovery addresses. This preview exists solely for UI/API testing and never proves email delivery. Staging/production create no fallback sender, expose recovery unavailable and fail closed until mail is valid; production still requires STARTTLS or implicit TLS and the production secret contract. Public forgot remains enumeration-safe, routes stay under backend auth-class IP throttling plus Caddy route body/timeout policies, and no permission or target-user mutation is introduced.
- `AuthSessionActive` is never cached: immediate session revoke remains authoritative even when Redis supplies distributed rate limiting and SSE Pub/Sub.
- The project explorer index cache is actor-scoped, not role-name scoped. Membership, staff-user linkage, user-role and role-permission mutations bump the affected actor revision in the same database transaction. Redis index IDs are still rechecked with current `ProjectAccessFilter` before any cached row is returned; cache keys or frontend visibility never authorize access.
- `roles.external_only` classifies business counterparts that cannot act in the App. V89 marks `client`, fails when migration would strand an external-only open work item/pending approval or a mixed-role user, removes App permissions, revokes sessions, inactivates linked users/staff/project memberships and preserves `user_roles` plus historical workflow/runtime labels. Login lookup, session creation/refresh/active checks, role edit, role-permission assignment, user-role assignment and project-member save all fail closed independently of frontend filtering.
- V68 adds the system roles `Thiết kế`, `Sale`, `Pháp lý` with the minimum permission sets needed by their official-workflow steps and grants existing `Đội thi công` pipeline/planning access. The migration does not auto-assign users or project memberships and does not broaden existing runtime role snapshots.
- Project-finance permissions are independent capability gates: view, material-cost create/review, cash-request create/approve/process, and management report view. Accounting owns capture/review/handoff processing, Director owns cash-request approval/reporting, and all actions still combine permission with project scope. Legacy ledger/tax permissions remain admin-only historical support.
- Manual posting, source posting, reversal, period close/reopen and migration-reconciliation resolution write actor/time/reason audit in the same transaction. Reconciliation resolution is one-way: a second resolution returns conflict and cannot overwrite the original conclusion.

## Cross-Domain Checks

- Staff deletion is a dedicated Admin/Developer governance transition, never a generic status edit. `staff.delete` and `staff.account_security.manage` are both required; preview/execute are server-authoritative, max 100 and all-or-nothing with self/last-active-Admin blockers. V114 preserves Staff/User rows, login-email uniqueness, business FKs and stored names while revoking sessions/tokens/roles, clearing recovery/first-password state and deactivating memberships; V115 owns the impact-query indexes without rewriting applied V114 bytes. Dynamic references add companion deletion flags; active selectors exclude deleted identities and immutable snapshots remain unchanged.

- Pair with every affected source domain when adding permissions, roles, navigation entries, project scopes, or row actions.
- Pair with commercial, quality, and accounting domains when partner catalog fields or snapshot semantics change.
- Check audit logs and actor propagation when changing any privileged action, approval action, or session lifecycle behavior.
