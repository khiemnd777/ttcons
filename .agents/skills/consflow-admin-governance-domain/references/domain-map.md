## Invariants

- `Bàn làm việc` remains actor-scoped. Its default `responsible` list scope separates direct assignment, matching project role and an unassigned department pool from same-department/all-visible oversight; summary buckets preserve the selected scope, while `waiting_decision` remains actor-decidable. This list classification never grants or removes mutation authority. Frontend work, decidable-approval and attention query keys include the authenticated User ID, stay disabled until the actor exists and reconnect actor-owned SSE on identity change; authentication bootstrap/failure/login/logout clears the shared query cache, so a prior account's fresh response cannot cross the identity boundary. First-load summary values remain pending/unavailable until an authoritative work response rather than presenting placeholder zeroes. Backend `execution_target` is a navigation hint produced only after ordinary list/detail scope; frontend accepts internal routes only. Cache keys, list-scope labels and the hint never replace project visibility, work-item action scope, source-module RBAC or mutation-time authorization, and unsafe/missing targets fail closed to guarded work-item detail.
- Protected endpoints stay under auth middleware.
- The shared IP rate limiter runs before JWT/session work. `AuthClaimsRequired` must stop on missing/invalid JWT; only verified claims supply the actor key, so actor rate limiting runs before authoritative `AuthSessionRequired`/`AuthSessionActive` DB validation. Heavy-route concurrency runs after the session gate. Rejected `401`/`429`/`503` requests never reach business/audit handlers; backpressure responses use the shared envelope with `Retry-After`. Trusted proxy CIDRs must identify only the immediate Caddy/internal proxy network.
- Backend permission helpers are the source of truth for authorization.
- Audit read APIs are server-filtered and page-number paginated, return project labels plus permission-scoped filter options, use global `ProjectAccessFilter` or project `requireProjectPermission`, and expose metadata read-only. Audit persistence is centralized in `backend/internal/core/audit.go`: critical governance/workflow/finance and quality approval/terminal mutations use the same DB transaction and fail closed; classified non-critical operational events remain best-effort but emit structured failure logs. Metadata serialization and insert errors must never be silently discarded on a critical transition.
- Event Logs are operational diagnostics, not business audit history. V111 reserves `event_log.view` for Admin/Developer at migration-trigger, repository replacement and seed layers; `audit.view` never implies access. Capture covers final backend unexpected 5xx, panic and controlled backend 503, while excluding 4xx/429, `/metrics`, liveness/readiness and Caddy-only gateway failures. Rows retain at most 90 days and store registered route, request class/ID, known actor/project context, deterministic fingerprint and sanitized diagnostics without request body, query string, auth header/cookie or raw IP. Persistence is best-effort and its failure emits only a secret-safe structured fallback; it must never replace the original response. Full message/stack remain detail-only. Public generic 500 responses and shared frontend 5xx toasts expose the same request ID.
- Activity reply/reaction/edit/withdraw endpoints remain protected and reuse `ActivityVisibleToUser`; edit/withdraw additionally require exact author ownership, activity type `comment`, an unwithdrawn row and the 15-minute server window. UI capability flags never replace backend enforcement, managers receive no override, and no new global permission is introduced.
- Frontend navigation and row actions mirror permissions but do not replace backend enforcement.
- V110 reserves Settings governance by capability and system role: Developer owns `settings.view|settings.update|seal.manage`; Admin retains `settings.view|seal.manage` but cannot receive `settings.update`; other roles cannot receive these reserved Settings/seal-management permissions. The backend role-permission replacement path enforces both boundaries, while frontend visibility is presentation only. Local seed supplies `developer@consflow.local`; migration never creates a production user.

V117 grants `project.import` only to Admin/Developer and `project.export` only to Admin/Developer/PM. - System settings use an explicit typed registry, optimistic row versions and fail-closed audit in one transaction. - Every new password uses one canonical backend/frontend contract: non-whitespace, at least 8 Unicode code points and at most 72 UTF-8 bytes. Self change, recovery reset and Admin replacement require an exact confirmation; only initial Staff account creation intentionally omits confirmation. Replacing an existing account password must differ from its current bcrypt credential. Login and current-password fields validate presence only because they verify an existing credential rather than create one. - Personal Profile is actor-owned and permission-free after authentication: neither self-service mutation accepts a target user ID. `/auth/me` uses `users` for login identity and a preferred non-deleted linked `staff` row for phone/department/position. Its actor-wide `roles` display summary returns each role display name once across global/project assignments; AppShell, Project Workspace, Profile and My Work reuse the shared trimmed unique presentation contract, while every scoped `user_roles` assignment remains intact for authorization. Email change requires the current password; password change requires current/matching confirmation and persists bcrypt only. Either sensitive change revokes every session and clears the refresh cookie so the JWT email used by later audit cannot remain stale. Audit records changed field names/session outcome only and never password material; historical audit/activity actor snapshots are not rewritten.
- Self-service recovery email is optional, actor-owned, users-only and never mirrored into `staff`. `/auth/me` exposes availability plus masked verified/pending values only. Shared masking exposes at most the first three local-part characters, the first domain character and final suffix (`abcdef@gmail.com` -> `abc***@g**.com`). Self set/replace/remove requires current password; a pending replacement cannot displace the old verified address. Separately, an actor with both `staff.update` and `staff.account_security.manage` may set a linked user's normalized recovery address through `PUT /staff/:id`, and an actor with both `staff.create` and `staff.account_security.manage` may supply it during `POST /staff`; either Admin path marks the address verified immediately without delivery or confirmation. `GET /staff` always exposes `has_recovery_email`, but only an actor with `staff.account_security.manage` receives `recovery_email_masked`; the full repository-only field is removed before the response. Blank Admin edit fields mean unchanged, every recovery address must differ from the actual login email and unlinked staff fail validation. Forgot accepts login email but returns one enumeration-safe response immediately; bounded background delivery sends only for active non-external accounts with a verified recovery address. Verification lasts 24h by default and reset lasts 15m by default; raw 256-bit tokens exist only in memory/email URL fragments while PostgreSQL stores SHA-256 hashes. Consumption rechecks active/non-external/verified-target state, is one-time and audit-atomic. Self reset or Admin password reset bcrypt-updates the password and revokes every target session; either Admin security change invalidates active recovery tokens. Audit/logs never contain password material, raw tokens or full recovery addresses; local `.local` seed accounts receive no recovery address.
- Staff account creation and security administration are governance actions, not recovery-delivery actions. `POST /staff` requires both `staff.create` and `staff.account_security.manage`, takes one initial password with no confirmation plus an optional recovery email, and creates the linked `users` and `staff` rows with two fail-closed audits in one transaction. Staff department and position are optional profile metadata, not authorization: whitespace-only values normalize to SQL `NULL`, explicit blank edits clear them, and omitting either update key preserves it. An absent department cannot satisfy department-only work routing until updated; role/staff/project assignment remains independent. No role is assigned implicitly; the independent shield action remains authoritative. `PUT /staff/:id` always requires `staff.update`; nonblank `new_password`/confirmation/recovery email additionally requires `staff.account_security.manage`. Staff edits reject direct user relinking, synchronize normalized full name/login email to the user and all linked non-deleted Staff rows, derive user active state from linked Staff rows and reject activation of an external-only account. Password, login-email or activation changes revoke target sessions; password and recovery changes invalidate active recovery tokens. A self-sensitive update returns `reauth_required` so the frontend clears its session. The Staff edit dialog uses one pencil and one combined form, keeps the replacement email input empty, shows the permission-scoped current mask as helper text and awaits authoritative refetch after a non-self save. Role/project replacement semantics remain unchanged.

The browser accepts exact 8-column `.xlsx`/`.csv` up to 1 MB/100 rows and sends structured rows; backend preview remains authoritative. The source file, password and recovery address are never stored in the batch/audit. Imported users carry `must_change_password`; DB-backed middleware permits only `/auth/me` and own password change until successful self-change or recovery reset clears the flag and revokes sessions.

Existing ready roles no-op, missing roles create linked active User/Staff with role display name, department `Dữ liệu mẫu`, the approved bcrypt credential and secret-free per-account/summary audit. `users.sample_role_id` is unique, and sample role grants are project-scoped only.

Membership, staff-user linkage, user-role and role-permission mutations bump the affected actor revision in the same database transaction. ## Notification Platform Boundary

- V126 registers governance/security catalog candidates (`project.member_*`, `project.role_changed`, `project.pm_changed`, `account.role_*`, account lifecycle) disabled. They must not be enabled until their authoritative admin transaction emits an idempotent event with an explicit recipient and a reviewed route; notification delivery may never replace session revocation, audit or permission synchronization.
- V130 enables the reviewed project-startup events and `work_item.assigned`. Single create and PM handover emit inside the authoritative audit transaction; batch import emits one importer summary rather than one notification per project. Dynamic visibility hides resolved/non-actionable startup and work-item notifications. `work_item_responsible` uses operational assignment scope without the global Admin intervention override, so permission to intervene never becomes a broadcast audience. Notification read/archive remains independent from resolving the startup source projection.
